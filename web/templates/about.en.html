How it works

What counts as a promise

A paper counts as promising code when it links its own GitHub repository, or says its code will be released. We look in two places:

  • The abstract and comments returned by the arXiv API.
  • The full text of the paper (the arXiv HTML version). A link in the body only counts when the sentence around it talks about the authors' own work, for example “Our code is available at …” or “Code: …”. Links in the references, and links to other people's code, never count.

We only include papers whose arXiv comment says they were accepted at the conference (for example “Accepted at ICLR 2025”). Workshop papers and papers “under review” are excluded.

How a repository is judged

We make a shallow clone of the repository's default branch and look at the files in its latest commit.

StatusRule
Code releasedSource files (.py, .ipynb, .cpp, .cu, .js, …) add up to at least 5 KB.
A few lines of codeSome source files, but less than 5 KB.
Data onlyNo source files, but at least 100 KB of data or model files (.json, .csv, .pt, .safetensors, …). Common for benchmark papers.
Empty repositoryNo source files and no meaningful data: only a README, a license or images.
Repository goneThe repository does not exist or is private.
No repository in the arXiv versionThe arXiv version says code will be released but gives no repository link, or links only to an anonymous review copy (anonymous.4open.science). Code hosted outside GitHub may be missed; please tell us.

“Promised N days ago” counts from the later of two dates: the first arXiv version of the paper, and the first day of the conference.

What counts as not delivered

Only three statuses count: empty repository, a few lines of code, and repository gone. “Data only” is not counted, because benchmark papers may only need to share data. “No repository in the arXiv version” is not counted either. The latest arXiv version of a paper is sometimes still the version written during double-blind review, and the code may have been published on a project page or elsewhere without updating arXiv.

Author checklists (extra information)

Many READMEs carry a checklist such as “- [x] Release inference code / - [ ] Release training code”. For papers whose code is released, the site also shows which items on the author's own checklist are not ticked yet. This is extra information. It is never counted as not delivered.

To avoid flagging anyone by mistake, only clear release promises count: items starting with Release, Open-source, Upload or Publish, or short items such as “Training code” or “Checkpoints”, about code, weights or data. Plans to extend the work (“more datasets”, “a new version”, “support for …”), struck-through items and items about the paper itself are ignored. An unticked training or inference item is treated as done when the repository already has matching files, such as train.py, since the author may simply have forgotten to tick it. The site quotes the checklist as it is and draws no further conclusion.

What we do not do

  • We do not show author names, and we do not judge anyone. A repository can be empty for good reasons; we only report what is there.
  • We only check the default branch. If the code lives on another branch or another site, please tell us.

Limitations

  • Only papers that mention the conference in their arXiv comment are covered, which is a bit under half of the accepted papers.
  • The full-text step depends on arXiv's HTML version, which some papers do not have.
